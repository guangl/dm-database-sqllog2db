    在 `src/error.rs` 中：

    **关于严重性前缀的说明（处理 checker WARNING — context_compliance）**：D-07 的错误格式示例使用 `[ERROR] No log files found matching inputs: ...`，但本计划将 `NoFilesFound` 归入 `ParserError`，沿用 `ParserError` 既有的 Warning 严重性（`Error::Parser(_) => ErrorSeverity::Warning`），最终 stderr 输出会显示为 `[WARNING] No log files found matching inputs: ...` 而非 `[ERROR]`。这是**可接受的偏差**：
    - D-07 示例中的 `[ERROR]` 仅为格式示例（"形如"），核心要求是"非匹配时返回错误而不是静默"——通过 `Result::Err` 返回路径达成
    - SC3 ROADMAP 成功标准要求"无匹配 inputs 时明确错误 + 退出码非零 + hint 行"——三项均由 `Err(Error::Parser(NoFilesFound))` + `format_error_output` 满足，与严重性标签字面值（`[ERROR]` vs `[WARNING]`）无关
    - 保持 `ParserError` 统一为 Warning 严重性可避免新增 `is_fatal`/`severity` 分支的局部异常，符合最小改动原则
    - Plan 03 的 e2e 测试只断言文本子串 `"No log files found matching inputs"` 与 `"hint:"`，不断言严重性标签字面值

    若未来 D-07 严格要求 `[ERROR]` 前缀，再单独提升 `NoFilesFound` 至 `is_fatal=true` 或新增顶层 `AppError::NoFilesFound` 变体；本 plan 不做此改动。

    具体修改：

    1) 扩展 `pub enum ParserError`（位于第 199-213 行附近），新增变体：
       ```
       NoFilesFound { inputs: Vec<String> },
       ```

       变体位置：放在 `ReadDirFailed` 之后

    4) 扩展 `impl Error::is_fatal()`：`Error::Parser(_) => false` 已统一返回 false，新变体自动归入 false 分支，无需新增匹配臂。
    5) 扩展 `impl Error::severity()`：`Error::Parser(_) => ErrorSeverity::Warning` 已统一返回 Warning，新变体自动归入，无需新增匹配臂（接受 `[WARNING]` 前缀，见上文说明）。
