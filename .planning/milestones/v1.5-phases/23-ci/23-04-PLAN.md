    Create .github/workflows/lychee.yml with the following configuration.

    **Workflow structure (follow existing CI patterns):**

    ```yaml
    name: Link Check

    on:
      push:
        branches: [main]
        paths:
          - 'README.md'
          - 'CHANGELOG.md'
          - 'docs/*.md'
          - 'site/**/*.md'
      pull_request:
        branches: [main]
        paths:
          - 'README.md'
          - 'CHANGELOG.md'
          - 'docs/*.md'
          - 'site/**/*.md'

    env:
      CARGO_TERM_COLOR: always

    jobs:
      link-check:
        name: Check Links
        runs-on: ubuntu-latest
        steps:
          - uses: actions/checkout@v6

          - name: Run lychee link checker
            uses: lycheeverse/lychee-action@v1
            with:
              args: >-
                --max-retries 3
                --timeout 30
                --verbose
                --no-progress
                --exclude-mail
                README.md
                CHANGELOG.md
                docs/
                site/
              fail: true
    ```

    **Key design decisions (mapped to user decisions):**

    1. **Scan scope** (D-08): Targets are README.md, CHANGELOG.md, docs/, site/. The `.planning/` directory is intentionally excluded since it only stores workflow/planning artifacts, not user-facing documentation. The lychee action scans entire directories recursively.

    2. **External link handling** (D-09): `--max-retries 3 --timeout 30` handles flaky external services. `fail: true` ensures any broken link (external or internal) blocks the CI. This matches D-09 ("失败阻塞CI") and D-11 ("内部链接失败直接阻塞CI") — both external and internal failures block the workflow.

    3. **Paths trigger** (D-10): The `on.push.paths` filter ensures the workflow only runs when Markdown files change. Changes to .rs files, Cargo.toml, config files, etc. will not trigger this workflow. The same filter applies to pull_request events for consistency.

    4. **URL exclusions**: Some external URLs may consistently fail due to rate limiting. Add `--exclude` patterns for known problematic services. Common candidates:
       - `crates.io` may rate-limit CI requests from shared IPs
       - `docs.rs` build-time URLs may return 404 until docs are published
       - GitHub shields.io badges are usually fine

       Add exclusions as needed based on testing. For example:
       ```
       --exclude https://crates.io/api
       --exclude https://docs.rs/crate
       ```

       Start without exclusions and add them in a follow-up if CI fails on false positives. The `--verbose` flag will show which URLs fail, making it easy to identify rate-limiting issues.

    5. **Fail mode**: `fail: true` ensures the workflow fails if ANY link is broken (external retries exhausted or internal path not found). This is consistent with both D-09 and D-11.

    **Formatting notes:**
    - Use the same indentation style as .github/workflows/ci.yaml (2-space YAML)
    - Use `actions/checkout@v6` to match existing workflows
    - Use `lycheeverse/lychee-action@v1` (latest stable major version)
    - Do NOT include `workflow_dispatch` — the workflow is purely automatic (per D-10 "仅 Markdown 文件变更时触发")
    - Do NOT include any `if:` condition on the job — let the paths filter handle triggers
    - Include `env: CARGO_TERM_COLOR: always` for consistency with existing workflows

This plan creates a CI workflow that runs the lychee link checker. The workflow executes outside the project's runtime environment and has access to GITHUB_TOKEN for repository access.

| Boundary | Description |
|----------|-------------|
| CI runner → Network | lychee makes HTTP requests to all URLs found in documentation |
| CI runner → GITHUB_TOKEN | Workflow has read access to the repository |
