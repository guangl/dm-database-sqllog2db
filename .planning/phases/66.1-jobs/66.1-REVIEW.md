# Phase 66.1: Code Review Report

**Reviewed:** 2026-06-04T00:00:00Z
**Depth:** standard
**Files Reviewed:** 8
**Status:** issues_found

## Summary

Phase 66.1 adds a `jobs_override: Option<usize>` parameter to `handle_run`, updates all call sites to pass `None`, adds the `write_heterogeneous_log` helper in `tests/integration.rs`, and introduces PARALLEL-06 and PARALLEL-07 integration tests that force parallel execution via `Some(2)`.

The implementation is structurally sound. The public API change is backwards-compatible (new parameter at the end, all callers updated). Three issues require attention before shipping: one silent panic footgun (`Some(0)` passes through to rayon without guard), one flaky test whose assertion holds only on single-threaded hosts, and one session ID collision risk in the new test helper that silently corrupts test data.

## Warnings

### WR-01: `jobs_override=Some(0)` panics at runtime — no guard on zero value

**File:** `src/cli/run/mod.rs:39-40`

**Issue:** When a caller passes `jobs_override = Some(0)`, the value 0 is used directly as the `jobs` variable. Both parallel conditions (`jobs > 1`) are false, so `run_sequential` is invoked — correct on its own. However, `scan_for_trxids_by_transaction_filters` receives `jobs = 0` via `merge_trxid_prescan` (line 41). Looking at how rayon uses the `jobs` parameter inside `prescan.rs` and `parallel.rs`, passing 0 to rayon's thread pool builder causes a panic ("Number of threads must be positive"). This panic is unrecoverable and produces no useful error message. The `jobs_override` parameter is documented as a test hook, but nothing in the type system prevents callers (including future tests) from passing zero. A zero value is a footgun with no guard and no explanation in the doc comment.

**Fix:**
```rust
// In handle_run, after computing jobs:
let jobs = jobs_override
    .unwrap_or_else(|| std::thread::available_parallelism().map_or(1, std::num::NonZero::get));
// Guard: treat 0 as 1 to avoid downstream panics in rayon thread pool builder.
let jobs = jobs.max(1);
```

Alternatively, change the parameter type to `Option<NonZero<usize>>` so the type system enforces the invariant at the call site.

### WR-02: PARALLEL-06 assertion on record count is load-bearing but fragile — test can silently pass without exercising the parallel path

**File:** `tests/integration.rs:2466-2511`

**Issue:** The test passes `Some(2)` to force `jobs = 2`. The parallel path requires `jobs > 1 && log_files.len() > 1`. Both inputs are given as bare file paths (not a directory), so `SqllogParser` discovers exactly those two files — this part is correct. However, `write_heterogeneous_log` is called with `trxid_offset=0` for file A (trxid 0..19) and `trxid_offset=1000` for file B (trxid 1000..1014). The session ID field is `sess:0x{trxid:04x}`. For trxid values ≥ 65536 the `:04x` format silently widens beyond 4 hex digits (no truncation), so uniqueness is preserved. This is fine for the current values (max 1014 < 0xFFFF). But the comment "强制并行路径在所有环境下被执行" is the actual claim — and this claim is only verified by the side-effect of checking the total record count. If the parallel path were silently skipped (e.g., `use_csv_parallel` condition changes) and the sequential path processed both files identically, the count assertion would still pass. There is no assertion that *verifies the parallel path was taken* (e.g., checking `verbose` output for the "[parallel]" label, or asserting run_stats has a non-zero skipped_files=0 and parallel flag is set). The test documents the intent well but does not prove the parallel path fired.

**Fix:** Add a parallel-path proof assertion. The simplest is to check the summary line that `handle_run` prints when `quiet=false`:
```rust
// Change quiet=true to quiet=false and capture stderr,
// then assert the output contains "[parallel]"
// OR: run with verbose=true and assert stderr contains
// "Processing X files in parallel (2 jobs)"
```

At minimum, use `quiet=false, verbose=true` and redirect stderr to a buffer, then assert the "in parallel" message appears.

### WR-03: `write_heterogeneous_log` session-ID field format differs from `write_test_log` — silent data divergence in PARALLEL-07 cross-comparison

**File:** `tests/integration.rs:31-52`

**Issue:** `write_test_log` uses `sess:0x{i:04x}` where `i` starts at 0 for every file. `write_heterogeneous_log` uses `sess:0x{trxid:04x}` where `trxid = trxid_offset + i`. In PARALLEL-07, the sequential baseline processes each file independently: file A generates sess IDs starting at `0x0000`, file B generates sess IDs starting at `0x03e8` (1000). The parallel path processes both files together and sees the same distribution. On its own this is correct. The problem is that PARALLEL-07's sequential baseline loop calls `handle_run` with a single-file `inputs` array. If the Config builder in the loop uses `inputs: vec![log_file.to_str()...]` pointing to the actual file path (not a directory), `SqllogParser` receives a file path and discovers the single file — matching what the parallel run would process. This is correct behavior.

However, `write_heterogeneous_log` omits `stmt:0x1` in its format string — it writes `stmt:0x1` inline in the format literal. Checking line 43-46:
```
"2025-01-15 10:30:28.001 (EP[0] sess:0x{trxid:04x} user:{username} trxid:{trxid} \
 stmt:0x1 appname:App ip:10.0.0.1) [SEL] SELECT * FROM t WHERE id={trxid}. \
 EXECTIME: {}(ms) ROWCOUNT: {}(rows) EXEC_ID: {trxid}.",
```
The positional `{}` arguments are `(trxid * 13) % 1000` (EXECTIME) and `trxid % 100` (ROWCOUNT). When `trxid = 0`, EXECTIME = 0 and ROWCOUNT = 0. A ROWCOUNT of 0 may trigger the `rowcount != 0` guard in `has_metrics` (per CLAUDE.md: "rowcount != 0 to avoid silent data loss"), which would cause the record to be exported without performance-metric fields populated. This means the CSV row for trxid=0 may differ structurally from rows with trxid > 0 — specifically, `exec_time_ms`, `row_count`, and `exec_id` columns may be empty. Both parallel and sequential paths would hit this same row, so the sorted-line comparison in PARALLEL-07 would still pass. But the test silently exercises an edge case (zero metrics) without asserting on it, and no test documents whether the PARALLEL-06/07 records with trxid=0 produce complete or partial rows.

**Fix:** Set `trxid_offset` in PARALLEL-06 to start at 1 (not 0) to avoid the zero-trxid edge case, or add an explicit assertion confirming the zero-trxid row is handled:
```rust
// PARALLEL-06: use trxid_offset=1 to avoid zero-metrics edge case
write_heterogeneous_log(&file_a, 20, 1, "USERA");
```

## Info

### IN-01: `jobs_override` parameter is a `pub` API surface change with no `#[doc(hidden)]` or stability annotation

**File:** `src/cli/run/mod.rs:29-35`

**Issue:** `handle_run` is `pub` and is re-exported from `lib.rs` (used by all integration tests and benchmarks via `dm_database_sqllog2db::cli::run::handle_run`). The new `jobs_override: Option<usize>` parameter is a test hook. No `#[doc(hidden)]` or stability warning marks it as unstable. External consumers (if any) must now pass `None` for every call. The doc comment documents the intent, but the signal is only in a comment, not the type.

**Fix:** Either mark the function `#[doc(hidden)]` if it is internal, or introduce a `RunOptions` builder struct to encapsulate flags so test-only fields don't pollute the primary API surface.

### IN-02: `test_parallel_csv_jobs_override_forces_parallel` (PARALLEL-06) uses quiet=true — hides the "[parallel]" indicator that would prove parallel execution

**File:** `tests/integration.rs:2496`

**Issue:** Passing `quiet=true` to `handle_run` suppresses the `eprintln!` that contains "[parallel]", so there is no observable signal from the run that the parallel path fired. The only observable outcome checked is the final record count (35). This is related to WR-02 but is a separate observation about test observability.

**Fix:** Use `quiet=false, verbose=true` and capture stderr via a pipe or a test-local redirect to assert the parallel path was actually selected. If that is impractical in unit test context, add a return value to `handle_run` (or use the existing `ErrorStats`) that carries a `mode: Sequential | Parallel` field.
