# Phase 66.1: 修复并行集成测试覆盖 — Research

**Researched:** 2026-06-04
**Domain:** Rust 测试工程 / rayon 并行控制 / 集成测试数据设计
**Confidence:** HIGH

## Summary

Phase 66 在 `tests/integration.rs` 中新增了三条并行集成测试
（`test_parallel_csv_content_matches_sequential`、
`test_parallel_csv_filter_matches_sequential`、
`test_handle_run_parallel_csv_multiple_files`），
但存在两个系统性缺陷，导致**并行路径在特定 CI 环境下可能根本不被执行**：

**缺陷 1：强制 jobs 参数缺失。**
`handle_run` 内部通过 `std::thread::available_parallelism()` 动态获取 CPU 核数作为
`jobs`，并用 `jobs > 1` 作为并行路径的触发条件之一。在单核 CI（如 GitHub Actions 免费
runner 的某些 Linux 镜像）或 macOS 虚拟机的部分配置下，`available_parallelism()` 返回
`1`，导致并行路径永远不触发。所有三条并行测试都通过 `handle_run` 调用，无法注入固定的
`jobs` 值，因此**无法保证并行路径被执行**。

**缺陷 2：测试数据同构。**
`write_test_log` 生成的日志数据中，所有文件的记录使用相同的字段模式（同一 user、同一
timestamp、trxid 从 0 开始连续递增）。当多个文件使用相同计数写入时（如
`write_test_log(&file_a, 20); write_test_log(&file_b, 20)`），两个文件中 id=0..19
的记录内容完全相同。这意味着：若并行路径存在记录遗漏 bug（例如某个文件的记录被覆盖），
排序后对比仍可能通过——因为两个文件有相同的行集合，无法区分"来自 a.log 的 id=5"
和"来自 b.log 的 id=5"。**异构数据才能暴露跨文件聚合错误。**

**Primary recommendation:** 新增一个直接调用 `process_csv_parallel` 的辅助函数（绕过
`handle_run` 的 `jobs` 检测逻辑），强制 `jobs=2`；同时将现有并行测试的数据改造为
异构数据（各文件使用不同的 user、trxid 空间、记录数）。

## 核心问题分析

### 问题 1：parallel 路径的触发条件

`src/cli/run/mod.rs` 第 37 行：
```rust
let jobs = std::thread::available_parallelism().map_or(1, std::num::NonZero::get);
```

第 62 行（CSV 并行条件）：
```rust
let use_csv_parallel =
    jobs > 1 && log_files.len() > 1 && !is_stdin_pipe && final_cfg.exporter.csv.is_some();
```

三个触发条件：
1. `jobs > 1` — 依赖运行时 CPU 核数，**不可被测试控制**
2. `log_files.len() > 1` — 可控（测试写多个文件）
3. `!is_stdin_pipe && csv.is_some()` — 可控

**结论：** `jobs > 1` 是唯一不可控的条件。在单核 CI 上 `jobs=1`，并行路径从不触发，
测试通过但等价于顺序路径（测试无价值）。

### 问题 2：write_test_log 生成的数据同构性

```rust
fn write_test_log(path: &std::path::Path, count: usize) {
    for i in 0..count {
        writeln!(buf,
            "2025-01-15 10:30:28.001 (EP[0] sess:0x{i:04x} user:TESTUSER trxid:{i} ...) SELECT * FROM t WHERE id={i}.",
        ...
        )
    }
}
```

当调用 `write_test_log(&file_a, 20)` 和 `write_test_log(&file_b, 20)` 时：
- 两个文件均产生 `id=0` 到 `id=19` 的完全相同记录
- 排序后集合比较：`seq_lines` 包含 40 个唯一行（a 的 20 + b 的 20），
  `par_lines` 即使只输出 20 行（仅 a 的记录），排序后 `len()` 断言就会失败——
  **但当 jobs=1 时并行路径根本不走，测试等同于顺序路径比较，必然通过。**

**两个缺陷叠加的效果：** 即使 jobs>1（多核机器），若并行实现有聚合 bug 导致某文件
记录被重复计数，而重复的行恰好与另一文件的行相同，排序后比较也可能无法检出。

### 解决方案分析

#### 强制 jobs 参数的可行方案

方案 A：**直接调用 `process_csv_parallel`（`pub(super)` 改为 `pub(crate)` 或通过
`mod tests` 访问）**，传入 `jobs=2`。  
[ASSUMED] 优缺点：完全绕过 `handle_run`，但需要暴露内部函数。

方案 B：**通过环境变量 `RAYON_NUM_THREADS=2` 影响 `available_parallelism`**。  
[VERIFIED: 代码审查] `handle_run` 使用的是 `std::thread::available_parallelism()`，
而 **不是** `rayon::current_num_threads()`。
`RAYON_NUM_THREADS` 只影响 rayon 全局线程池，不影响 `available_parallelism()` 的返回值。
因此此方案**无效**。

方案 C：**在 `handle_run` 签名上添加可选 `jobs_override: Option<usize>` 参数**，
测试传入 `Some(2)`，生产代码传入 `None`。  
优点：最直接，对接口侵入性最小；缺点：改变了公共函数签名，需要更新所有调用点。

方案 D：**将 `process_csv_parallel` 改为 `pub(crate)` 并在
`tests::integration` 的 helper 中直接构造调用链**（构造 Pipeline、FieldMask 等参数）。  
优点：无需改 `handle_run` 签名；缺点：测试代码需要了解更多内部结构，维护成本较高。

方案 E：**新增独立的 test-only 帮助函数 `handle_run_with_jobs`** 仅供测试调用。  
[ASSUMED] 最干净，无需破坏生产代码接口。

**推荐方案 C（参数注入）**，理由：
1. `handle_run` 已是 `pub` 函数，集成测试直接调用，注入 override 最自然
2. 调用点只有 `main.rs` 一处（生产代码），传 `None` 即保持原有行为
3. 不需要暴露 `process_csv_parallel` 等内部函数
4. 方案明确、可审查、易测试

#### 异构测试数据的设计

需要新的 helper，让每个文件的记录在以下维度上可区分：
- **不同 user 字段**（如 `USERFILE_A` vs `USERFILE_B`）
- **不同 trxid 空间**（文件 A 用 0..20，文件 B 用 1000..1020，无重叠）
- **不同记录数**（如文件 A 20 条，文件 B 15 条）
- **不同 SQL 语句**（包含文件标识符）

这样，若并行路径漏掉文件 B 的所有记录，`seq_lines.len() = 35` vs `par_lines.len() = 20`，
`assert_eq!` 立刻失败——而使用同构数据时若两个文件完全一致，这种检测取决于 set 大小。

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| 并行控制 | 自定义 thread spawn 逻辑 | `rayon::ThreadPoolBuilder::num_threads(jobs)` | 已有完整实现 |
| 测试隔离 | 全局 rayon 线程数设置 | `jobs_override` 注入 + 独立 ThreadPool | 避免测试并发干扰 |
| 记录唯一性 | 复杂 hash 校验 | trxid/username offset 使各文件记录天然可区分 | 简单可靠 |

## Common Pitfalls

### Pitfall 1：RAYON_NUM_THREADS 无效
**What goes wrong:** 试图用 `std::env::set_var("RAYON_NUM_THREADS", "2")` 控制并行，
但 `handle_run` 调用的是 `std::thread::available_parallelism()`，该函数读取 OS 核数，
与 rayon 环境变量无关。
**Why it happens:** rayon 全局线程池默认读取 `RAYON_NUM_THREADS`，但
`available_parallelism()` 是标准库函数，不受其影响。
**How to avoid:** 不要依赖环境变量；使用 `jobs_override` 参数直接注入。
**Warning signs:** 设置环境变量后并行路径仍不触发（因为 jobs 仍由 OS 决定）。

### Pitfall 2：同构数据导致假阳性通过
**What goes wrong:** 测试用 `write_test_log(&a, N); write_test_log(&b, N)`，
两个文件内容完全相同，排序后集合比较不能区分"a 文件所有记录 + b 文件无记录"
vs "两文件各出 N 条记录"——只要 `a.len() + b.len() == total` 且内容相同就通过。
**How to avoid:** 用不同 user/trxid/offset 使两文件记录不重叠。

### Pitfall 3：改 handle_run 签名影响其他调用点
**What goes wrong:** `handle_run` 在 `src/main.rs` 和 `tests/integration.rs` 都有
直接调用，添加参数后所有调用点必须同步更新，否则编译失败。
**How to avoid:** 使用 `cargo build` 作为一次性检查；调用点很少（main.rs 1 处，
tests 内多处），批量更新成本低。

### Pitfall 4：忘记验证 jobs=1 时的回退行为
**What goes wrong:** 添加 `jobs_override` 后，原有的单线程路径测试（如
`test_handle_run_real_csv_export`）应仍然正确，不需要修改。
**How to avoid:** 确认 `jobs_override=None` 时行为与修改前完全一致（回退到
`available_parallelism()`）。

pub fn handle_run(
    cfg: &Config,
    quiet: bool,
    verbose: bool,
    interrupted: &Arc<AtomicBool>,
    jobs_override: Option<usize>,  // None = 使用 available_parallelism

        std::thread::available_parallelism().map_or(1, std::num::NonZero::get)

}

### 异构测试数据 helper（建议新增）
```rust
// tests/integration.rs — 新增 helper
fn write_heterogeneous_log(
    path: &std::path::Path,
    count: usize,
    trxid_offset: usize,   // 不同文件使用不重叠的 trxid 空间
    username: &str,         // 不同文件使用不同用户名
) {
    use std::fmt::Write as _;
    let mut buf = String::with_capacity(count * 200);
    for i in 0..count {
        let trxid = trxid_offset + i;
        writeln!(
            buf,
            "2025-01-15 10:30:28.001 (EP[0] sess:0x{trxid:04x} user:{username} trxid:{trxid} \
             stmt:0x1 appname:App ip:10.0.0.1) [SEL] SELECT * FROM t WHERE id={trxid}. \
             EXECTIME: {}(ms) ROWCOUNT: {}(rows) EXEC_ID: {trxid}.",
            (trxid * 13) % 1000,
            trxid % 100,
        ).unwrap();
    }
    std::fs::write(path, buf).unwrap();
}
```
